# ИИ-помощник покупателя

Открытые материалы кейса хакатона ЮФУ, 20–22 ноября 2026 года. Версия контракта — **1.1**.

Создайте помощника, который понимает запрос покупателя, уточняет недостающие условия и подбирает комплект из учебного каталога. Для разбора запроса или продолжения диалога используйте **Gemma 4 31B через API организаторов**. Способ поиска, фильтрации и подсчёта цены выбирает команда.

За получением ключа доступа обращайтесь к [@ynwaks](https://t.me/ynwaks) в Telegram.

## Запуск решения

Из корня репозитория команды проверяющий вызывает исполняемый файл `run`.

```sh
./run --catalog /absolute/path/catalog.json < /absolute/path/request.json > /absolute/path/response.json
```

Для открытых примеров пути к запросам — `examples/01-selection/request.json` и `examples/02-clarification/request.json`. Каталог обоих примеров — `data/catalog.json`.

Решение читает один JSON из stdin и возвращает один JSON в stdout. Логи направляйте в stderr. Полная история диалога приходит в каждом запросе. Подробные правила находятся в [контракте](CONTRACT.md).

Основной CLI и каждый запрос `/api/buy` всегда вызывают Gemma для NLU, затем
сверяют результат с локальным
разбором истории. Каталог в модель не передаётся. Для Python backend нужны только
стандартная библиотека и доступ к шлюзу через `LLM_BASE_URL`, `LLM_MODEL`,
`LLM_API_KEY`, `LLM_USER_AGENT`; OpenSearch и веса локальных моделей не нужны.

После строгой проверки структурированных условий `select(listings, requirements,
preferences=())` оценивает положительные текстовые пожелания по названию и описанию.
Используются нормализация словоформ и небольшой словарь близких понятий. Оценка
пожелания — доля совпавших понятий, от 0 до 10000; пожелания усредняются внутри
категории, оценки категорий суммируются для комплекта. Повторы слов не повышают
балл. Просматриваются все комбинации допустимых объявлений (до 578676 при 250
товарах), сохраняются три лучших в пределах бюджета. При равенстве баллов
предпочитается меньшая цена, затем лексикографический порядок ID в порядке
категорий. Без совпадений пожеланий используется прежний поиск трёх самых дешёвых
комплектов. Мягкие пожелания ширины, температуры и регулировки высоты получают
10000 за подтверждённое соответствие структурированного атрибута и 0 за отсутствие
соответствия или неизвестное значение. Они усредняются с текстовыми пожеланиями,
никогда не добавляя фильтров; описание не подтверждает числовое совпадение.

Поддержка категории определяется по `data/categories.json`, независимо от наличия
объявлений. Gemma распознаёт запрошенные товары во внутреннем `requested_categories`;
backend проверяет их ID по справочнику и сверяет с локальным разбором диалога.
Аналогично города проверяются по `data/cities.json`. Внутренний `requested_location`
содержит распознанный тип места, исходное название и ID. Регистр и падеж не
определяют поддержку. Неизвестный город даёт `clarify` с полем `city_id`, сообщением
«Такого города нет. Пожалуйста, выберите из имеющихся», динамическим списком городов
и введённым названием. Поиск в прежнем городе блокируется; бюджет, категории и
пожелания сохраняются. Выбор доступного города продолжает подбор, «город неважен»
снимает неподдерживаемый город и оставляет обычное уточнение. Отсутствие объявлений
в поддерживаемом городе по-прежнему определяется поиском и даёт `no_match`.
Географические подсказки локального разбора только вызывают NLU; случайное слово
после предлога не считается подтверждённым городом.
Для неподдерживаемого товара возвращается `clarify`: «Такого каталога нет.
Пожалуйста, выберите из имеющихся», затем названия из справочника. Старая подборка
не выдаётся, совместимые город, бюджет, характеристики и пожелания сохраняются.
Выбор поддерживаемого товара после отказа продолжает подбор; неизвестный товар
не становится пожеланием. Если категория поддерживается, но объявлений нет,
возвращается `no_match` с указанием отсутствующей категории. Если объявления есть,
но строгие условия исключают их, `no_match` объясняет причину фильтрации.
Числа в контексте ширины/температуры резервируются до разбора бюджета. Без ясной
единицы требуется уточнить характеристику. В официальном CLI такой вопрос
использует разрешённое поле `categories`: схема не допускает `width_cm` в questions.
Число с `км`, `м`, `см`, `мм` (включая полные формы единиц) резервируется вместе
с единицей и не становится деньгами. `13.000` и `13 000` читаются как 13000;
десятичная запятая сохраняется. Расстояние, высота, длина и глубина стола дают
`clarify`, поскольку этих условий нет в схеме. Размеры ширины в см/мм и явно
названная ширина в метрах обрабатываются прежними фильтрами.
В диалоге с измерениями числовое значение бюджета Gemma проверяется по локально
подтверждённой денежной сумме; наличие других рублей не подтверждает число с км.
Числовые границы ширины и температуры сверяются с локальным разбором истории.
Цена отдельного товара (`стоит`, `цена кресла`, `кресло 1400 рублей`) требует
уточнения и не меняет прежний общий бюджет или состав. `Бюджет`, `на весь комплект`
и однозначный максимум покупки (`стол до 5000 рублей`) обрабатываются как бюджет.
Запись с точкой и тремя цифрами трактуется как группировка тысяч, а не дробь;
для дробных значений используйте запятую. Неизвестные единицы и сложные числительные
не образуют новые атрибуты каталога и могут потребовать уточнения.
Голое «до 100» без валюты и контекста бюджета не подтверждает сумму.

Каждая новая реплика проверяется отдельно: посторонняя тема и неоднозначная цена
предмета дают `clarify`, сохраняя контекст покупки без повторной выдачи старых
комплектов. Внутренний `intent` Gemma не попадает в официальный JSON. Явное
«новый диалог» обрезает историю и сбрасывает условия. Отмена предыдущего
пожелания учитывается и при повторном разборе истории моделью.
Если город и поддерживаемые категории уже известны, пустой результат строгих
фильтров даёт `no_match` даже без бюджета: уточнять сумму при доказанном отсутствии
товаров не нужно. Если допустимые товары есть, недостающий бюджет уточняется.
Техническая ошибка поиска остаётся технической ошибкой.

Необязательный indexed-режим демо использует ограниченный пул: три дешёвых и до
восьми релевантных по заголовку объявлений на категорию; в hybrid-режиме дешёвый
пул увеличен до 16. Каждое числовое/булево пожелание дополнительно извлекает до
восьми самых дешёвых совпадений через структурированную filter-агрегацию внутри
обязательных фильтров. Эти пожелания не сужают основной запрос. Совпадения повторно
проверяются на backend; числовая оценка участвует в рейтинге полного комплекта.
При сочетании текста и чисел две оценки нормируются до одной шкалы и усредняются
внутри категории. Его ранжирование не гарантирует глобально точный порядок всего
каталога. Минимумы по цене сохраняют проверку выполнимости бюджета. Ошибки связи,
шардов и неполные агрегации считаются техническими ошибками. Основной CLI использует
полный допустимый пул переданного JSON и не обращается к OpenSearch.

Для тестов и проверки официальной JSON Schema нужна только дополнительная
зависимость разработки; она не импортируется основным CLI:

```sh
python3 -m pip install -r tests/requirements.txt
python3 -m unittest discover -v
python3 -m tests.check_lifecycle --repeats 2
python3 -m bench.local_cli --repeats 30 --output bench/results/local-cli.json
```

Web API записывает только числовую диагностику этапов в stderr и HTTP-заголовок
`Server-Timing`: `gemma_ms`, `resolve_ms`, `search_ms`, `total_ms`. Время Gemma
входит в `resolve_ms`, поэтому эти два значения не суммируются. Поиск измеряется
отдельно после NLU. Тексты сообщений и заголовки авторизации в диагностику не
попадают; JSON CLI остаётся прежним. Реальный замер 15 сценариев (включая два на
`data/catalog.json`): `python3 -m bench.stage_latency --output bench/results/new-stage-run.json`.
Выбирайте новый путь отчёта при каждом запуске. Это диагностика, без изменения
алгоритмов поиска, retry или timeout.

Функциональные проверки frontend без дополнительных зависимостей: `node tests/ui_dialogue.cjs`.

### Голосовой ввод в веб-демо

Кнопка «Голосовой ввод» рядом с отправкой запускает Web Speech API только после
нажатия. Поддерживаются `SpeechRecognition` и `webkitSpeechRecognition`, язык
`ru-RU`, непрерывные и промежуточные результаты. Кнопка «Остановить запись»
завершает диктовку. Временный текст убирается, окончательные фрагменты дополняют
уже введённый текст. Затем можно отредактировать запрос и нажать кнопку отправки
или Enter. Во время записи отправка заблокирована. Автоматического перезапуска нет.
Смена вкладки на «Проверка защиты» останавливает запись; «Новый диалог» отменяет
её и очищает поле вместе с историей. Во время серверного запроса микрофон отключён.

Распознавание не меняет историю или условия и не обращается к backend/Gemma.
Подтверждённый текст проходит через прежний `submit(text)` и `/api/buy`.
При ошибке API он остаётся в поле для повтора. Обрабатываются запрет микрофона
и сервиса, отсутствие микрофона, тишина, сетевые ошибки, недоступный русский язык,
отмена и ошибка запуска. При отсутствии API текстовый ввод остаётся доступен.

Для демо откройте `http://localhost:8765`; при удалённом размещении используйте
HTTPS. Фактическая доступность API и русского распознавания зависит от браузера,
его настроек и сервиса. Некоторые браузеры передают звук своему поставщику
распознавания: работа полностью локально не гарантируется. Приложение не создаёт
аудиофайлов, не сохраняет аудио, не передаёт его в Python или Gemma и не пишет
расшифровки в технические логи. Возможности API описаны в
[документации Web Speech API](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition).

DOM-тесты запускают настоящий `app.js` с mock DOM, fetch и обоими вариантами API.
Они проверяют накопление результатов, явную отправку, историю, ошибки и гонки
между остановкой, сбросом и повторной записью. Это не проверка реального микрофона.
Ручная проверка Chrome была остановлена инструментом управления браузером,
который не смог надёжно определить URL. Диктовка в Chrome, Edge и мобильном
браузере фактически не проверена; поддержку этих браузеров этот прогон не подтверждает.

Ручная проверка перед демонстрацией (выполнить отдельно в Chrome, Edge и на
мобильном браузере с API; зафиксировать версию браузера и результат):

- Разрешить микрофон, продиктовать «Стол в Азове до пяти тысяч рублей», остановить
  запись. Проверить итоговый текст, исправить его и отправить. Только после
  отправки должен появиться POST `/api/buy`.
- Запретить разрешение: убедиться в понятной подсказке и сохранении набранного текста.
- Запустить запись и молчать; затем проверить фоновый шум: пустой запрос не отправляется.
- Продиктовать длинную русскую фразу с паузами, городом, бюджетом и размерами:
  промежуточные фрагменты не должны дублироваться в итоговом тексте.
- Повторить диктант в непустом поле; проверить сохранение первого текста и возможность
  редактирования, затем короткий голосовой ответ на уточнение в текущем диалоге.
- Во время записи проверить Enter, «Новый диалог» и переход в «Проверка защиты»:
  отправка блокируется, отменённый текст не появляется снова.
- Проверить запуск с клавиатуры, видимый фокус, озвучивание статуса, ширину экрана
  320–390 px и режим уменьшенной анимации. Проверить запасной текстовый ввод при
  отсутствии SpeechRecognition или недоступности сервиса распознавания.

`check_lifecycle` повторяет весь набор в одном процессе и проверяет закрытие
HTTP-серверов, завершение созданных потоков и дочерних процессов. Диагностика
не увеличивает таймауты тестов; она печатает счётчики ресурсов после каждого прогона.

Реальные проверки запускаются последовательно после заполнения корневого `.env`
по `llm/.env.example`. Ключ остаётся только в игнорируемом файле. Live-harness
проверяет срок доступа и официальный адрес, не допускает переопределения файла
другой конфигурацией окружения и останавливается при отказе авторизации.

```sh
python3 tests/live.py
python3 -m bench.real_quality
python3 -m bench.dialogue_live --output-prefix dialogue-web-new-run
python3 -m bench.unsupported_live --output-prefix unsupported-new-run
python3 -m bench.unsupported_cities_live --output-prefix unsupported-cities-new-run
python3 -m bench.numeric_units_live --output-prefix numeric-units-new-run
python3 -m bench.real_web
python3 bench/llm.py
```

Это настоящие обращения к API: запускайте команды по очереди. Интервал между
основными вызовами — не менее 7 секунд; учитывается `Retry-After`. Существующий
HTTP-клиент Gemma не подменяется: live-наблюдатель только сохраняет очищенные
ответы и метаданные обращений, не читая заголовки запросов. Результаты пишутся
в отдельные `bench/results/live-gemma-*`, старые `live.txt` и `llm.json` сохраняются.
Для повторных проверок предусмотрен `--output-prefix`, а у NLU-набора — `--case`.
`bench.unsupported_live` проверяет восемь сценариев: четыре неизвестных товара,
сохранение города и бюджета, продолжение после отказа, отсутствие объявлений
поддерживаемой категории и отсутствие соответствия строгим условиям. Он отдельно
проверяет распознанные самой Gemma товары и сохраняет отчёт с HTTP-трассировкой.

Бенчмарк поднимает локальный mock gateway, проверяет настоящий `run` и сохраняет
сырые измерения и P50/P95. Время NLU в этом отчёте включает HTTP mock, а не
реальный инференс Gemma. Python pipeline измеряется после импорта модулей;
`fresh_run_process` дополнительно включает запуск bash/Python и импорты.

## Необязательный поиск по фотографии

Кнопка «Поиск по фото» открывает независимый блок: выбор или перетаскивание одного
файла, локальный предпросмотр, явный поиск, удаление фото и карточки объявлений.
Этот режим не пишет в историю, не меняет условия, пожелания или результат обычного
диалога и не вызывает Gemma. Текстовый и голосовой ввод используют прежний путь.
Визуальный режим показывает реальное покрытие текущего каталога: в демонстрации
это 18 из 111 объявлений, по шесть столов, кресел и ламп. Изображения явно синтетические;
они не являются фотографиями продавцов и не подтверждают характеристики товара.

Основной запуск остаётся прежним, без установки vision-зависимостей:

```powershell
.\.venv\Scripts\python.exe -m buyer.demo --port 8765
```

Установите необязательные зависимости один раз:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-vision.txt
```

При первом открытии «Поиск по фото» сервер сам проверяет модель, при необходимости
скачивает её, строит индекс и калибрует поиск. Процент загрузки рассчитан по байтам.
Проверенные веса и актуальный индекс повторно используются после перезапуска.
При ошибке интерфейс предлагает повторить подготовку или показывает команду
установки зависимостей. Для предварительной подготовки перед показом:

```powershell
.\.venv\Scripts\python.exe scripts/prepare_visual_demo.py --download
.\.venv\Scripts\python.exe scripts/prepare_visual_demo.py --check
```

Для показа откройте «Поиск по фото», выберите пример «Стол» и нажмите «Найти похожие товары». Пейзаж показывает сценарий без совпадения. В статусе видны готовность и покрытие, а при отсутствии индекса или весов — инструкция по настройке. `npm run dev` предпочитает Python из проектной `.venv`.

Отдельные команды подготовки:

```powershell
.\.venv\Scripts\python.exe scripts/download_vision_model.py
.\.venv\Scripts\python.exe scripts/build_visual_index.py
# Для новой коллекции изображений также нужна повторная калибровка:
.\.venv\Scripts\python.exe scripts/calibrate_visual_search.py
```

Модель — [nomic-ai/nomic-embed-vision-v1.5](https://huggingface.co/nomic-ai/nomic-embed-vision-v1.5),

`POST /api/visual-search` принимает multipart с одним полем `image`. URL не
принимаются; имя файла и MIME клиента не используются для определения формата или
пути. JPEG/PNG/WebP проверяются декодером, максимум 5 MiB и сторона 2048 px,
EXIF учитывается, изображение переводится в RGB, анимация и повреждённые файлы
отвергаются. Файлы загрузок не сохраняются, фото не попадают в логи.
`GET /visual-images/products/...` отдаёт только разрешённые manifest изображения,
связанные с текущими ID. В CSP локальный `blob:` разрешён только для изображений.

При открытии фото-режима отдельный процесс проверяет готовность и подготавливает
локальные данные при необходимости. Блокировка между процессами исключает
одновременную установку. Изменение LF/CRLF в manifest не инвалидирует калибровку.
Модель остаётся в этом процессе, embeddings каталога не пересчитываются в API.
Один visual-запрос обрабатывается одновременно; у Gemma отдельный semaphore.
Чтение тела ограничено 10 секундами, обработка worker — 30 секундами. На Windows
worker помещается в Job Object с лимитом private commit 1 GiB, на Unix — RLIMIT_AS
3 GiB. NumPy/ONNX используют ограниченное число потоков. Если создать ограниченный
worker нельзя, он аварийно завершается или истёк timeout, отключается только
визуальный режим. На shutdown worker завершается вместе с сервером.

Отдельные статусы фото-API: `ok`, `visual_no_match`, `visual_unavailable`,
`invalid_image`, `visual_busy`. Они не входят в официальный CLI-контракт.
Отсутствие модуля, зависимостей, весов, manifest или индекса даёт контролируемую
недоступность. Маршруты `/api/buy`, `/api/catalog`, `/api/lab` и `./run` сохраняют
свой контракт и не загружают vision. Можно удалить `buyer/vision`, `data/visual`,
`models/vision`, `cache/visual`: основной сервер и CLI продолжают работать.

## Что сдавать

Репозиторий с исходным кодом, исполняемым `run`, зависимостями с версиями и README. В README опишите установку, запуск и место использования модели. Подключение читайте из `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` и `LLM_USER_AGENT`: проверяющий может заменить их при запуске. Организатор передаёт каждой команде её ключ лично. Значения ключей храните отдельно от репозитория. На защите покажите сценарий в веб-интерфейсе, боте или консоли.
